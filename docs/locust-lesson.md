# Дополнительный практикум с Locust

Продолжительность: 50–60 минут. Понадобятся браузер и PowerShell. Все команды выполняются из корня проекта. На этой машине одновременно работают приложение, генератор и мониторинг, поэтому результаты нужны для обучения, а не для оценки производительности сервера.

## Что получится к концу занятия

Вы сможете отличить медленный ответ от ошибки, прочитать RPS и p95, сопоставить пользовательскую статистику Locust с метриками Flask и сформулировать проверяемую гипотезу о причине проблемы.

## 1. Запуск и карта стенда — 5 минут

```powershell
.\scripts\Start-Lab.ps1
```

Откройте:

| Сервис | Адрес | Зачем нужен |
|---|---|---|
| Flask | http://localhost:5000 | Приложение, на которое направляем запросы |
| Locust | http://localhost:8089 | Виртуальные пользователи, RPS, ошибки и время ответа |
| Grafana | http://localhost:3000 | Графики приложения и генератора за выбранное время |
| Prometheus | http://localhost:9090/targets | Проверка, что сбор метрик работает |

В Grafana откройте папку учебной лаборатории и дашборды Flask и Locust. Выберите последние 15 минут и автообновление 5 секунд. В Prometheus у целей Flask и Locust должен быть статус UP. Если сразу после запуска графики пусты, дождитесь нескольких сборов: для `rate()` нужны хотя бы две точки.

Для первого запуска используйте [инструкцию Locust](locust.md).

Проследите путь: **Locust → HTTP-запрос → Flask → HTTP-ответ**. Отдельно **Prometheus → `/metrics` → Grafana**. Grafana показывает уже собранные значения и сама не создаёт нагрузку.

## 2. Базовый сценарий — 8 минут

В Locust нажмите Start/New test. Укажите Host `http://127.0.0.1:5000` при нативном запуске или `http://flask:5000` в Docker. Выберите 10 пользователей, скорость запуска 2 пользователя в секунду и сценарий `baseline` в поле `lab-scenario`. Дайте тесту поработать 60 секунд и нажмите Stop.

Альтернатива без браузерного управления:

```powershell
.\scripts\Run-LoadTest.ps1 -Scenario baseline -Users 10 -Duration 60s
```

Выберите один способ на всё занятие: Web UI или команды. Скрипт создаёт отдельный процесс Locust; его результаты смотрите в `reports/<UTC-время>-<сценарий>/report.html` и на дашборде Grafana с генератором `locust_headless`. Статистика браузерного Locust на 8089 относится только к тестам из Web UI; для них в Grafana выбирайте `locust`. Перед командой остановите активный тест в Web UI. Команды принимают 1–100 пользователей и длительность от `10s` до `5m`.

Сценарий вызывает `/api/fast`. Зафиксируйте средний RPS, p95, долю ошибок и CPU. Числа будут зависеть от компьютера. Не выбирайте отдельный случайный пик как итог всего теста.

До следующего запуска дождитесь завершения текущего теста. Статистика Locust относится к текущему тесту; Grafana продолжает хранить предыдущие интервалы. В UI сбросьте статистику перед новым самостоятельным измерением, если Locust её сохранил.

## 3. Медленные ответы — 10 минут

Выберите сценарий `slow`, те же 10 пользователей и 60 секунд:

```powershell
.\scripts\Run-LoadTest.ps1 -Scenario slow -Users 10 -Duration 60s
```

Теперь каждый запрос к `/api/slow` намеренно ждёт 250 мс. Сравните с базовым запуском:

- выросло ли время ответа;
- снизился ли RPS при неизменном числе пользователей;
- выросла ли доля ошибок;
- вырос ли CPU настолько же заметно, как p95.

Ожидание ответа занимает время, даже если CPU почти свободен. При фиксированном числе пользователей более медленный запрос обычно уменьшает RPS: пользователь должен получить ответ и выдержать паузу перед следующим запросом.

Задание: предскажите результат 20 пользователей. Проверьте один раз и объясните, почему двукратный рост пользователей не гарантирует двукратный рост RPS.

## 4. Ошибки при быстром ответе — 8 минут

Запустите `errors` с 10 пользователями на 60 секунд:

```powershell
.\scripts\Run-LoadTest.ps1 -Scenario errors -Users 10 -Duration 60s
```

`/api/flaky` возвращает HTTP 503 с вероятностью 15%. Locust намеренно считает эти ответы неуспешными. Доля за короткий тест будет колебаться вокруг 15%, а не обязана совпадать с ней точно.

Найдите ошибки в Locust Web UI или в HTML-отчёте автоматического запуска, затем линию HTTP 5xx в Grafana. Сравните p95 с предыдущим сценарием. Быстрый ответ 503 всё равно является ошибкой для пользователя. Не называйте такой тест успешным только из-за малого времени ответа.

## 5. Работа на CPU — 8 минут

```powershell
.\scripts\Run-LoadTest.ps1 -Scenario cpu -Users 10 -Duration 60s
```

Сценарий `/api/cpu` выполняет вычисления. Смотрите одновременно CPU процесса, число запросов в работе, RPS и p95. Затем один раз сравните с 20 пользователями. CPU и хвост задержек зависят от мощности компьютера, числа потоков и конкуренции за интерпретатор Python; заметное насыщение при этих небольших параметрах не гарантируется.

Сформулируйте гипотезу до изменения параметра: «Если причина в вычислениях, то увеличение их объёма должно …». Изменяйте по одному параметру, чтобы результат можно было объяснить.

## 6. Смешанная нагрузка и итог — 10 минут

```powershell
.\scripts\Run-LoadTest.ps1 -Scenario mixed -Users 15 -Duration 90s
```

Смешанный профиль выбирает `/api/fast`, `/api/slow`, `/api/flaky`, `/api/cpu` с весами 8:2:1:1. Это вероятности выбора, а не гарантированный состав завершённых запросов. Посмотрите разбиение по маршрутам: общий p95 может скрывать различия между ними.

Заполните таблицу по своим запускам:

| Сценарий | Пользователи | RPS | p95 | Ошибки, % | Наблюдение и гипотеза |
|---|---:|---:|---:|---:|---|
| baseline | 10 | | | | |
| slow | 10 | | | | |
| errors | 10 | | | | |
| cpu | 10 | | | | |
| mixed | 15 | | | | |

Ответьте письменно: какой маршрут ухудшал задержку, какой давал ошибки, какой создавал вычислительную работу и какие метрики подтверждают каждый вывод. Завершите занятие:

```powershell
.\scripts\Stop-Lab.ps1
```

## Как читать показатели

**RPS** — сколько запросов завершается за секунду. **10 пользователей** — число одновременно работающих сценариев, а не 10 запросов в секунду. Между запросами здесь есть случайная пауза 150–500 мс.

**p95 = 300 мс** означает: примерно 95% наблюдавшихся ответов укладываются в 300 мс, остальные медленнее. Это не максимальное время ответа и не среднее. При малом числе запросов перцентили нестабильны.

**Доля ошибок** — неуспешные запросы / все запросы. HTTP 503 в `errors` ожидаем по замыслу упражнения. Ошибки соединения или тайм-ауты в `baseline` требуют проверки стенда.

**CPU** на графике процесса показывает загрузку в долях одного ядра. Не путайте её с загрузкой всего компьютера. Метрики CPU и памяти приложения здесь собираются через `psutil` и доступны в Windows и Linux.

**Время в Flask и в Locust различается**: Flask измеряет обработку запроса внутри приложения, Locust — клиентское ожидание ответа, включая сеть и обслуживание соединения. Сбор `/metrics` и проверки `/health` не должны попадать в учебный HTTP-трафик на дашборде.

Источники: [документация Locust о настройках и отчётах](https://docs.locust.io/en/stable/configuration.html), [параметры в Web UI](https://docs.locust.io/en/stable/extending-locust.html#custom-arguments), [Prometheus о гистограммах и перцентилях](https://prometheus.io/docs/practices/histograms/).
